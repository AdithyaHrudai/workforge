The domain

Four contract types, not one

This is the decision the whole product is organised around. Contract manpower is not a single thing, and the category a requirement belongs to determines what the company specifies, what the contractor quotes, and how the two are compared.

Category The company specifies The contractor quotes Basis
White-collar staffingEngineers, supervisors, executives Roles and headcount Rate per person / month, headcount offered Per person
Blue-collar staffingOperators, technicians, tradesmen Roles and headcount Rate per person / month, headcount offered Per person
Job contractShutdowns, mould change, loading Scope of work and an output target Rate per tonne / unit / lump sum — no headcount Per output
Unskilled supplyHelpers, loaders, housekeeping Roles and headcount Rate per person / month, headcount offered Per person
The differentiator

The job contract is what most systems get wrong. The company buys an outcome — 300 tonnes loaded per day, 18 mould changes per shift, a shutdown completed — and how many people or machines to deploy is the contractor's commercial call.

WorkForge therefore never asks for a headcount on a job contract. This is enforced in the validation schema, not just hidden in the form: the proposal shape for that category cannot carry a headcount field.

How contractors are judged

Two signals, and the search filters and ranks on both. The client list — every contractor publishes which companies they serve, at which plant, in which state, how many people, since when. That is what tells a plant in Chhattisgarh who already has people on the ground there. Admins verify entries against work orders and mark them.

Five rating parameters, filed by the company after each completed engagement: timely deployment, statutory compliance, timely payment to workers, manpower quality, and supervision. Averages are denormalised onto the profile so search can rank on any one of them without aggregating per query.

Runtime

One application, no separate API

There is no detached backend service. The application renders on the server and mutates through server actions — typed functions the browser calls directly. That removes an entire REST layer, and with it a class of bugs where the API and the UI disagree about what a valid request looks like.

Edgemiddleware.ts
First filter on every request. Verifies the session signature and attaches a per-request nonce Content Security Policy.
  • Deliberately does no database work, so it cannot check suspension — it is a cheap gate, never the access control itself.
Pagesapp/ — 34 routes
React Server Components. Each protected page and layout independently calls requireUser() or requireRole() — authorisation is re-proved at the page, not inherited from the edge.
Server actionsapp/actions/ — 9 modules
Every mutation. One module per domain area: auth, company, contractor, requirements, proposals, engagement, messaging, notifications, admin.
  • Each action re-checks the role, validates with Zod, and rate-limits before touching data.
Domain logiclib/ — 21 modules
Where the rules live, kept out of the UI: contractor ↔ requirement matching, search, contact visibility, profile completeness scoring, validation schemas, the audit trail, notifications and email.
DataPrisma → PostgreSQL
Typed queries against Postgres. Multi-valued attributes (presence states, sectors, categories) are native text[] columns with GIN indexes, because the search filters on them by overlap.

Trust

Security and data protection

Credentials

Passwords are bcrypt hashes. The passwordHash field is referenced in exactly two places in the codebase — hashing at registration, comparison at login. It is never selected into a page, a response or a log line.

Login compares against a dummy hash when the email is unknown, so a missing account and a wrong password take the same time. The form cannot be used to discover who is registered.

Sessions

Signed httpOnly cookies, secure in production. Each carries a token version mirroring the user record.

Suspending an account or changing a password increments it, which invalidates every session that account already holds — immediately, rather than waiting for a cookie to expire.

Uploaded documents

Stored in the database rather than object storage, so there is no public bucket to misconfigure. Served only to the owner or an admin, with the file type confirmed by inspecting the bytes rather than trusting the browser.

Each is returned under a sandbox CSP, so a script embedded in a crafted PDF has no origin to act against.

Abuse limits

Rate limiting is Postgres-backed rather than in-memory, because serverless instances are ephemeral and do not share state.

Applied to registration, login (by IP and by email), uploads, messages, proposals, postings and invitations.

Oversight that is itself accountable

Admins can see every registered account and every privileged action. Because that is a genuine privacy exposure, using it is logged too: opening a contractor or company review page, or running a user search, writes an entry recording who looked, at what, and what it matched. Those rows are highlighted in the audit view.

The trail is append-only — there is no edit or delete path anywhere in the codebase, because a log an administrator can rewrite is not evidence of anything.

Also in place

Per-request nonce Content Security Policy; HSTS with preload; server actions accepted only from the application's own origin, with no wildcards; clickjacking and MIME-sniffing protections; authenticated pages marked never to be indexed or cached by shared proxies. Data is encrypted at rest by the database provider.

Operations

Deployment and assurance

How it runs

Vercel for the application, Neon for Postgres, hosted in Singapore for latency and data residency. Because documents live in the database, no object storage is required — which keeps the deployment to two services. A Dockerfile is included if a container host is preferred later.

How it is checked

A build that type-checks the whole application is the release gate. Beyond that, a suite of 45 automated checks asserts every route's status code and, more importantly, the access-control matrix — that a contractor cannot reach company pages, that a non-participant cannot read an engagement, that the public directory stays public while contact details stay gated.
